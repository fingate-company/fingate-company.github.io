## 3. Problem

**Eyebrow**  
WHY AX

**Headline**  
AI를 도입했는데,  
왜 팀의 속도는 그대로일까요?

**Lead**  
코드와 화면을 만드는 비용은 낮아졌지만, 무엇을 만들지 결정하고 맞는지 검증하는 방식은 그대로이기 때문입니다.

**Problem 01 — 개인에게 머무는 AI**  
각자 AI는 잘 쓰지만 결과와 노하우가 팀의 표준으로 축적되지 않습니다.

**Problem 02 — 반복되는 전달과 대기**  
기획에서 디자인, 개발, 검증으로 넘어갈 때마다 맥락이 빠지고 확인과 재작업이 반복됩니다.

**Problem 03 — 마지막에 몰리는 검증**  
문서와 검사, 보고가 프로젝트 후반에 몰리면서 문제를 늦게 발견하고 같은 일을 다시 만듭니다.

**Closing statement**  
병목은 실행에서 결정과 검증으로 이동했습니다. 이제 도구가 아니라 일하는 방식을 바꿔야 합니다.

## 4. Definition

**Eyebrow**  
FINGATE AX SYSTEM

**Headline**  
도구 도입이 아니라,  
일하는 방식의 전환입니다

**Definition**  
핀게이트 AX는 하나의 기준 문서를 중심으로 AI가 반복 실무를 수행하고, 자동 검증과 사람의 승인을 거쳐 결과를 반영하는 통제된 개발 체계입니다.

**Flow**

1. 하나의 기준 — 요구사항, 정책, 화면, 연동 규격을 하나의 기준으로 정리합니다.
2. AI 수행 — 설계, 코드, 테스트, 문서와 보고를 기준에 맞춰 생성합니다.
3. 자동 검증 — 산출물이 기준과 일치하는지 반복해서 검사하고 수정합니다.
4. 사람 승인 — 사람이 결과와 근거를 확인한 뒤 반영 여부를 결정합니다.
5. 기록 축적 — 변경, 검증, 승인, 진척 이력이 다음 업무의 자산으로 남습니다.

**Principle**  
AI가 만드는 일을 맡고, 사람은 기준을 정하고 판단합니다. 승인되지 않은 결과는 반영되지 않습니다.

## 10. FAQ

### AI가 만든 결과를 믿어도 됩니까?

믿는 대신 검증합니다. 기준 대조, 자동 검사, 사람 승인까지 통과한 결과만 시스템에 반영합니다.

### 우리 데이터가 외부로 나가지 않습니까?

업무 데이터와 소스코드의 저장 위치는 고객의 보안 정책에 맞춥니다. 외부 처리가 필요한 경우에도 허용된 요청만 전달하고 그 이력을 남깁니다.

### 기존 개발 조직은 어떻게 됩니까?

역할이 없어지는 것이 아니라 반복 작업에서 판단과 승인 중심으로 이동합니다. 공동 수행과 교육을 통해 고객 조직이 직접 운영할 수 있도록 지원합니다.

### 모든 기술 스택에 적용할 수 있습니까?

현재 구조와 컨벤션을 먼저 진단하고, 고객 환경에 맞는 하네스와 기준을 구성합니다. 기술적 전제가 맞지 않는 영역은 진단 단계에서 명확히 구분합니다.

### 같은 절감률을 보장합니까?

아닙니다. 공개된 AS-IS 수치는 실제 수행 기록이며, AX TO-BE는 동일 범위를 전제로 한 보수적 재산정입니다. 고객사의 효과는 대상 시스템을 진단하고 작은 과제로 실증해 확인합니다.
